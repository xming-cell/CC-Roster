## 0. 为什么重排

- 旧 `docs/task-plan.md` 基于“一个工具 = 一个好友”的微信式需求；新 IA 已改为“工具 / 供应商 / 项目 / 会话 / 操作记录”，顶层导航也变为工作台、供应商、操作记录、用量、设置。
- 后端保留了旧计划 002–022 的大部分实现：工具发现、供应商（Profile）CRUD、切换与快照、健康检查、会话回放、应用内对话、用量、审计、设置、外观、启动器、引导、桌面壳都已有代码和测试。继续按旧卡从零排期会重复劳动。
- 前端已回退到只有健康状态和工具列表的最小骨架；新 IA 的主要新增工作量在**前端重建**，后端只是增量适配。
- 旧卡 005/006/011 等与新 IA 的命名、页面结构和数据关系已经不一致，需要重新映射。

**本计划只规划剩余工作，不重开仓库、不重写后端。**

### 2.1 D-9 的具体建议（推荐 A）

- 「供应商」= 现有 `Profile` 实体；「供应商页」不新增持久化实体，只是**按工具分组的视图**。
- 「供应商」就是现有 `Profile`（协议、地址、模型清单、密钥引用）。
- 一个工具可以绑定多个供应商，其中一个 active；这正好对应 IA 的「工具列表显示已有供应商，以及正在使用的供应商」。
- 保留现有 `Profile` 可跨工具复用的能力，不破坏需求 F-03。
- 后端只需把 `ToolBinding` 从“一工具一条”放宽为“一工具多条、最多一条 active”；`ToolBinding.active` 字段已经存在。
- 如果选 B，则 102 必须先新增 `Archive` 模型、存储和迁移，工作量会明显上升。

### 101 — 前端应用壳与工作台工具列表

- 优先级：P0
- 依赖：100
- 对应 IA：§3、§4.1、§6
- 目标：做出新 IA 的应用壳和工作台第一屏，让用户能“看工具 → 看状态 → 决定下一步”。

**退出条件（DoD）**
- 应用壳有稳定导航；只显示已具备可用页面和空/错状态的入口，不摆空壳。
- 工作台默认入口：左侧工具列表，右侧当前工具详情/空状态。
- **不做搜索框**（ADR-014）：列表不提供搜索/筛选，靠分组与键盘跳转解决。
- 工具列表展示名称、安装/配置状态、当前供应商与模型摘要；异常和未配置项可见但不隐藏正常项。
- 加载、空列表、解析失败、部分失败、未选中都有明确状态。
- 复用或重构 `api/tools.ts`、`stores/tools.ts`；不新增重复请求层。
- 键盘可达、focus 可见、对比度满足基本可访问性；组件测试用 `getByRole` / `getByText`。
- `check.py` 退出码 0；手动验收“3 秒能识别为工具列表”。

**任务**
- [ ] T1 应用壳、导航、路由与页面占位策略。
- [ ] T2 全局 tokens 落地（CSS 变量）与基础布局。
- [ ] T3 工作台工具列表。
- [ ] T4 工具详情面板（从现有 `ToolDetailPanel` 重构）。
- [ ] T5 空 / 加载 / 错误 / 部分失败状态。
- [ ] T6 可访问性与响应式。
- [ ] T7 组件测试。
- [ ] T8 手动验收并记录。

**边界**
- 未配置工具仍可进入详情。
- 单个工具读取失败不阻塞其他工具。
- 扫描中不得先显示“正常”再跳变。

### 102 — 后端多供应商绑定与供应商视图

- 优先级：P0
- 依赖：100
- 对应 IA：§2、§4.3
- 目标：让一个工具保存多个供应商，其中一个生效，为供应商页和切换提供数据基础。

**退出条件（DoD）**
- `ProfileStore` 允许同一工具有多条绑定，但最多一条 `active=true`。

- 切换应用后只切换 active，不丢其他供应商。
- 删除供应商的占用检查覆盖所有绑定；已卸载工具仍参与占用提示。
- 现有单绑定数据可读；如需 schema 版本升级，有迁移与回退说明。
- 现有 526 个测试保持通过，并新增多绑定 / 单 active / 迁移 / 删除保护测试。

### 103 — 供应商页：供应商列表与 CRUD

- 优先级：P0

- 目标：让用户按工具管理供应商，能新增、编辑、复制、删除、体检，并清楚看到当前使用哪一个。

**退出条件（DoD）**

- 空 / 加载 / 错误 / 权限不足 / 密钥缺失都有可读状态。
