# 028 — 后端多供应商绑定与供应商视图

> 来源：`docs/task-plan2.md` §5 的 102 号规划卡；正式编号 028（沿用上一卡「目录用规划编号、标题用正式编号」的约定）。
> 依赖：100（V2 决策与设计基线）已完成；ADR-009（供应商语义）、ADR-010（一工具多供应商绑定）已定稿。101 的前端工作台 T1–T7 已完成，T8 手动验收待做，不阻塞本卡。
> 性质：后端实现卡。只动 `backend/src/**` 与 `backend/tests/**`；不改前端页面，不写工具配置文件。

## 背景与目标

1. 当前 `ProfileStore` 强制「同一工具只能有一条绑定」，`ProfileService.bind_tool` 和 `SwitchService._save_binding` 会用新绑定整体替换该工具的旧绑定。这与 ADR-010 冲突：用户需要在同一工具下保存多个供应商，并只把其中一个设为 active。
2. 本卡先补数据模型、服务语义和查询 API，为 103 的供应商页、104 的切换 / 预览 / 回滚提供稳定的数据基础；不提前做前端。
3. 目标按优先级：
   - 同一工具可保存多条不同供应商的绑定，最多一条 `active=true`；
   - 新增绑定不删除旧绑定，解绑只删指定供应商；
   - 切换只改变 active 与其他绑定的 active 状态，不丢绑定；
   - 删除保护覆盖所有绑定，包括已卸载工具的历次绑定；
   - 旧单绑定数据可直接读取，不要求破坏性迁移。

## 验收标准（DoD）

- `uv run python scripts/check.py` 退出码 0；现有 640 个后端测试保持通过，新增测试覆盖本卡行为。
- 数据完整性：
  - `ProfileStore` 允许同一 `tool_id` 对应多条 `ToolBinding`，但 `(tool_id, profile_id)` 不得重复。
  - 同一 `tool_id` 至多一条 `active=true`；零条 active 合法；读取到两条 active 时按档案库损坏报可读错误，不猜测哪条生效。
  - 绑定仍必须引用已存在的 `profile_id`；档案 id 重复继续报错。
  - 旧 `schema_version=1` 的单绑定文件可直接读取；本期不升 schema 版本（JSON 形状未变）。若实现中发现必须升版，需在本卡记录幂等迁移与回退说明。
- 绑定 API：
  - `PUT /api/tools/{tool_id}/profile` 新增一条绑定，不删除该工具的其他绑定；同一 `(tool_id, profile_id)` 重复调用幂等，不产生重复记录，`bound_at` 保持不变。
  - 绑定本身不等于激活：新绑定的 `active` 默认为 `false`；激活仍由切换 / 应用流程负责。
  - 解绑必须精确指定供应商：优先新增 `DELETE /api/tools/{tool_id}/profiles/{profile_id}`；旧 `DELETE /api/tools/{tool_id}/profile` 不得再清空该工具全部绑定，必须要求 `profile_id` 或改为等价的安全语义。
  - 解绑不存在的绑定返回 `removed=false`；未知工具 / 未知档案继续走现有 404 语义；不得因解绑一条绑定误删同工具的其他绑定。
  - 解绑当前 active 绑定后不自动提升其他绑定；该工具变为「无 active」，由后续切换流程决定。
- 切换 / 应用：
  - `SwitchService._save_binding` 只把目标 `(tool_id, profile_id)` 设为 `active=true`，并把该工具其他绑定设为 `active=false`；不得删除其他绑定。
  - 目标绑定已存在时保留原 `bound_at`；首次切换创建绑定时使用应用时间。
  - A→B→A 连续切换后两条绑定都保留，且始终恰好一条 active；`applied_at` / `snapshot_id` 指向最后一次成功应用。
  - 切换失败或回滚时不得留下两条 active、半写入绑定或丢失旧绑定。
- 删除保护：
  - 删除供应商前检查引用该 `profile_id` 的所有绑定，不按工具是否仍安装过滤。
  - 未确认删除仍有占用时返回 409 `PROFILE_IN_USE`；`used_by` 包含已卸载工具，且 `installed=false`。
  - 确认删除只移除该供应商的绑定，其他供应商的绑定不受影响。
- 查询 API：
  - `GET /api/profiles?tool_id=<id>` 返回该工具绑定的供应商与绑定；不带 `tool_id` 时保持现有全量行为。
  - `tool_id` 过滤不要求工具当前已安装；已卸载工具的历次绑定仍可查询。
  - 响应继续使用 `ProfileListResponse`，`secret_store` / `warnings` 语义不变；不暴露明文密钥或 `SecretRef`。
- 本卡不写工具配置文件；`profiles.json` 之外不产生新文件，读取 / 查询不修改文件。

## 边界用例（实现时必须想到）

1. 同一工具绑定同一供应商两次：幂等，`bound_at` 不变，不出现重复记录。
2. 同一工具绑定两个供应商：各自独立保留；两个都可以 `active=false`，切换时只改目标。
3. 同一供应商绑定多个工具：允许，删除保护必须列出全部工具。
4. 同一工具出现两条 `active=true`：读取 / 写入校验均拒绝，报可读的档案库错误，不静默修复。
5. 解绑 active 绑定但不解绑其他绑定：不自动提升其他绑定，返回成功并让工具进入无 active 状态。
6. 删除供应商时存在已卸载工具的历史绑定：仍视为占用，未确认 409，确认后精确清理。
7. 旧单绑定 `profiles.json`：直接读取并保持兼容；不因为放宽多绑定而要求改写文件。
8. 两个请求并发绑定 / 切换同一工具：文件锁内重新读取，最终最多一条 active，且不丢其他绑定。
9. 未知工具 / 未知档案：沿用现有 404；失败路径不产生半写入。
10. `tool_id` 过滤值为空白：返回 422 校验错误；未提供过滤参数时保持全量列表。

- 不做写入工具配置文件、快照生成、审计记录（104）；本卡只维护 `profiles.json` 的绑定关系。
- 不做供应商导入、去重、版本化 JSON（105）。
- 不重命名后端 `Profile` 实体，不新增 `Archive` 实体（ADR-009）。
- 不新增依赖；不扩展 `Profile` 的业务字段。
