# 024b — V2 任务总表与剩余任务卡

> 来源：`docs/task-plan2.md` 的执行视图。规划理由看计划书，这张卡只解决「怎么跟踪」。
> 正式编号沿用「目录用规划编号、标题用正式编号」；本卡属于规划收口，用 `024b` 后缀，不占用后续正式号。

## 背景与目标

1. 100–103 已完成，104–109 尚未建卡；计划书是长文，无法一眼看出当前做到哪、下一步是谁、设计稿是否已确认。
2. 目标 1：新增 `docs/task-board.md`，作为唯一的进度与设计确认视图，后续每张卡开工 / 设计确认 / 完成时更新。
3. 目标 2：把 104–109 正式建成任务卡，填好 DoD、scope、边界与不做项，避免开工时再返工拆卡。
4. 目标 3：把「前端先出 Penpot 设计、用户确认后再写代码」固定成流程，并记录在总表里。

## 验收标准（DoD）

- `uv run python scripts/check.py` 退出码 0。
- `docs/task-board.md` 包含：状态图例、卡片总表（规划号 / 正式号 / 目录 / 状态 / 依赖 / 设计稿）、设计确认记录、当前与下一步、固定流程。
- `docs/task-plan2.md` 顶部指向总表，读者不用翻到底就知道进度在哪。
- `specs/104-*` 到 `specs/109-*` 六个目录均有 `spec.md`（含 DoD / scope / 边界 / 不做）与 `tasks.md`。
- 104–108 的 spec 明确写出「Penpot 出稿并获用户确认」是前端开工前置条件；109 明确真人 E2E 与三平台 CI 不可由测试替代。
- `PROGRESS.md` 记录总表位置与当前指针含义。

## 边界用例（实现时必须想到）

1. 状态词必须来自固定图例，不能出现「差不多完成」这类无法判定的状态。
2. 103 实现时没有独立画板，必须在设计确认记录里如实标注，不能伪装成已设计。
3. 规划号与正式编号不一致时，以目录为准，标题里的正式号只用于沟通。
4. 任务卡新增或改名后，总表与 `specs/CURRENT` 必须同步，不能只改一处。

## 不做（明确划界）

- 不写任何业务代码、不改前端 / 后端实现。
- 不在本卡替 104–109 做技术选型或提前实现；只把已知约束写进卡片。
- 不引入外部看板工具；进度只维护在仓库内。
